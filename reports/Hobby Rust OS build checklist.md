# Real hardware gates Aeon's next steps

Aeon already covers more of the classic kernel spine than any teaching reference except the large projects: a signed UEFI image, W^X paging, a LAPIC timer, a preemptive round-robin scheduler, ring 3 through syscall, TPM measured boot and boot recovery. The research points to one conclusion. **The biggest gaps are not exotic kernel features. They are the three things that stop Aeon from being usable and testable on a real laptop: no keyboard after ExitBootServices on USB-only machines, no real disk driver (only virtio-blk), and no room to add any code, because the unsigned image is 261,632 of 262,144 bytes (512 bytes free).** Closing those needs an owner decision on two open questions (whether third-party crates are allowed, and whether the 256 KiB limit is a hard constraint or a project choice) before any driver work starts. After that, the sourced build order puts an ACPI/IOAPIC step, per-process page tables and an ELF loader next, then FAT write support. Testing is cheap to improve: the CI workflow exists but has never run, and fuzzing, Miri and a `SAFETY:` lint are the sourced next additions. KASLR, stack canaries, CET and speculative-execution mitigations were not researched, so this report ranks them as "research first", not as work items. Section 6 holds the prioritized gap table. Size figures for drivers are the researchers' own estimates, not measured counts, and each unsourced claim is tagged in the text.

How to read the tags: a bare citation means the researchers fetched the page, though the fetch tool paraphrases pages, so exact wording is not guaranteed. "(snippet)" means search-result text only. "(blog)", "(forum)" and "(bug report)" mean a non-authoritative source. "(inference)" is the researchers' or my own reasoning.

## 1. Boot path: one signed image is a legitimate design, but it takes on the loader's work

Mainstream loaders are separate programs that load a kernel file. The mainstream precedent for a kernel that is itself an EFI application is the Linux EFI stub, where the bzImage gets an EFI entry point so firmware runs it directly ([kernel.org EFI stub guide](https://www.kernel.org/doc/Documentation/admin-guide/efi-stub.rst), snippet), and the systemd-stub Unified Kernel Image, which embeds sections in one PE file and measures them into PCR 11 ([systemd TPM2 PCR measurements](https://systemd.io/TPM2_PCR_MEASUREMENTS/)). So Aeon's "bootloader stage and kernel together" is closer to a UKI than to GRUB. Limine and Redox take the other route. Limine hands the kernel a documented environment (typed memory map, framebuffer descriptors with optional EDID and mode list, RSDP address, HHDM offset) ([Limine PROTOCOL.md](https://github.com/limine-bootloader/limine/blob/v7.x/PROTOCOL.md)). Redox's Rust bootloader sets up the memory map and display mode, finds the RedoxFS partition, loads kernel and initfs, then jumps ([Redox book, boot process](https://doc.redox-os.org/book/boot-process.html), snippet). Since 0.7.0 it shares code between BIOS and UEFI and reuses the OS filesystem driver ([Redox 0.7.0 notes](https://redox-os.org/news/release-0.7.0), snippet). No source compares the two designs directly, so the trade-off below is inference: a one-image kernel does its own file access, GOP setup, memory-map capture and ACPI discovery before its allocator exists, and every kernel change is also a loader change and a re-signing event.

For Aeon the image limit changes this from a style choice into a practical one. With 512 bytes free, no driver, ELF loader or splash bitmap fits. The options are (a) lift the limit, if it is a project choice and not a firmware or ESP constraint, (b) split the Dawn stage from a kernel file, as Limine and Redox do, at the cost of a second verification step that the loader must perform and measure (inference), or (c) move code out of the image, which an ELF loader does for the five built-in ring-3 programs (inference). The owner should confirm where the 256 KiB figure comes from, because nothing in the notes explains it.

### Menu and countdown

The fetched primary pages agree on a pattern. systemd-boot shows no menu when no timeout is set and boots the default entry at once; pressing a key during boot shows the menu ([systemd BOOT docs](https://systemd.io/BOOT/)). The same docs warn that with timeout 0 the "hold a key" window may be short on some firmware and suggest a non-zero timeout instead. GRUB treats a timeout of 0 as "boot the default immediately without displaying the menu" and -1 as wait forever ([GNU GRUB manual](https://www.gnu.org/software/grub/manual/grub/html_node/timeout.html)). rEFInd treats 0 as wait indefinitely and -1 as boot at once, while a shortcut key still selects a target ([rEFInd config docs](https://rodsbooks.com/refind/configfile.html)). Windows' default `bootmenupolicy` is Standard, which shows the menu only on failure or with multiple entries ([Microsoft BCDEdit /set](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/bcdedit--set)). Aeon's 1-second Dawn countdown is therefore consistent with the sourced practice, and it is the more dependable choice than a pure hold-key design (inference, from the systemd advice). Two details are worth copying: systemd-boot's hotkeys include `f` to reboot to firmware, and it stores timeout changes in an EFI variable ([sd-boot(7)](https://www.freedesktop.org/software/systemd/man/258/sd-boot.html)). One caution from a bug report: GRUB's overlapping hidden-menu settings misbehaved on Ubuntu 24.10, so keep one timeout value and one menu-mode setting ([Ubuntu bug 2100718](https://lists.snapcraft.io/archives/foundations-bugs/2025-March/534182.html), bug report).

### Fast boot and the firmware setup key

No source gives per-stage boot times, so none are given here. What a loader controls is its own countdown, its file loading and any long GOP mode sets; it cannot shorten firmware POST or kernel init (inference). Measure first with timestamped serial output. The firmware setup key (F2, Del) is read by firmware during its own POST, before any loader runs. A loader can only request that the next boot stop in firmware setup, by setting bit 0x1 of the `OsIndications` variable, and only when `OsIndicationsSupported` advertises it; the firmware clears the bit after use ([UEFI 2.10 Runtime Services](https://uefi.org/specs/UEFI/2.10/08_Services_Runtime_Services.html), snippet). The pattern to copy is: read the supported bit, hide the menu entry if absent, set the bit, reset ([bootmgr-rs-core firmware.rs](https://docs.rs/crate/bootmgr-rs-core/latest/source/src/boot/action/firmware.rs), snippet; [FreeBSD review D32634](https://reviews.freebsd.org/D32634), code review). Whether Aeon has this entry is not stated in the supplied facts; verify.

### Secure Boot and measured boot

Aeon's signed image and TPM measured boot are the two items the notes describe as mature mainstream practice. Shim plus MOK and SBAT revocation only matter if Aeon chains through a third-party-signed loader; an image signed with a key in the firmware's db does not need them (inference). systemd's documented measured-boot layout (loader.conf into PCR 5, command line into PCR 12, UKI sections into PCR 11) is systemd-specific, so a custom kernel must emit its own TCG event-log entries (inference) ([systemd TPM2 PCR measurements](https://systemd.io/TPM2_PCR_MEASUREMENTS/)). No gap is listed here for Aeon beyond reviewing what its event log records against that layout.

## 2. Kernel essentials: the sourced order, and where Aeon sits in it

The only sourced ordering is blog_os's: exceptions, double faults, hardware interrupts, paging, heap and allocator designs, then async multitasking, with no user mode, ELF loading or syscalls ([os.phil-opp.com](https://os.phil-opp.com/)). The full UEFI spine below is the researchers' hypothesis, not a sourced consensus (inference). It is consistent with the dependency facts: a heap needs mapped pages, IST stacks are needed for double faults, MSI needs PCI enumeration plus a working LAPIC, and SMP needs the LAPIC and MADT. Aeon status comes from the supplied facts.

| Step | Why this order | Aeon status |
|---|---|---|
| UEFI handoff: memory map, RSDP, framebuffer | Everything later depends on it | Done (one image); RSDP capture not confirmed |
| GDT/TSS with IST stacks, IDT, exception handlers | Double faults need IST | Implied by ring 3 and LAPIC timer; IST not confirmed |
| Frame allocator, page tables, kernel heap, W^X | Heap needs mapped pages | Done |
| ACPI tables (MADT, FADT, MCFG) | Gives IOAPIC, overrides, PCI config space | Not listed; no IOAPIC |
| Mask legacy PIC, LAPIC, IOAPIC, timer calibration | Spurious PIC interrupts if unmasked | LAPIC timer done; IOAPIC missing |
| Kernel-thread scheduler | Needs a timer | Done, with a real ready queue |
| Syscall entry (syscall/sysret) | Needs a scheduler for blocking | Done |
| Per-process PML4 with shared kernel half | Isolation, loader target | Missing: one shared address space |
| ELF loader, first ring-3 entry from file | Needs a per-process space | Missing: 5 built-in programs |
| Drivers: PCI, storage, USB input | Need interrupts or polling | PCI scan and virtio-blk read-only only |
| Filesystem with writes, VFS | Needs a block device | FAT read-only, RAM filesystem |
| Networking | Needs driver plus stack | Missing |
| SMP | Needs LAPIC, MADT, per-CPU data | Missing |

The interrupt step has solid sourcing. The MADT lists local APICs (type 0), I/O APICs (type 1) and interrupt source overrides (type 2); the PIT is IRQ 0 but usually wired to GSI 2, so routing must consult overrides, and without an override ISA defaults to edge-triggered, active high ([osdev.wiki MADT](https://osdev.wiki/wiki/MADT)). Enabling the LAPIC needs bit 11 of `IA32_APIC_BASE` and the spurious-vector register's bit 8, and EOI is a write of 0 to offset 0xB0; the PIC should be masked and remapped first ([osdev.wiki APIC](https://osdev.wiki/wiki/APIC)). SMP bring-up is INIT, then SIPI, from the BSP only, with no broadcast IPIs, a trampoline in the first 1 MB on a 4 KiB boundary, and one stack per core ([osdev.wiki SMP](https://osdev.wiki/wiki/Symmetric_Multiprocessing)). GS-base per-CPU data and TLB shootdown were not sourced. Deferring SMP until address spaces work is opinion, not a finding.

### Address spaces and the ELF loader

The notes found no hobby-kernel loader to cite beyond a summary of SerenityOS. Its `AddressSpace.cpp` (about 425 lines, from a tool summary) owns a `PageDirectory`, creates it with `try_create_for_userspace`, and delegates PTE writes to the region code; it covers only the user range and does not copy regions on creation ([SerenityOS AddressSpace.cpp](https://github.com/SerenityOS/serenity/blob/master/Kernel/Memory/AddressSpace.cpp)). The minimal design is a PML4 per process, a kernel half shared across all PML4s and a user half owned by the process (inference). The xv6 book covers the same ground in chapters 1 and 3, and names `kernel/exec.c` and `kernel/vm.c` ([xv6 book rev5](https://pdos.csail.mit.edu/6.1810/2025/xv6/book-riscv-rev5.pdf)); OSTEP chapters 13 to 15 are the textbook match ([OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/)). The ELF loader can start from the RAM filesystem and does not need a disk driver (inference).

### Drivers: keyboard, storage, filesystems, network

The researchers' size estimates (not sourced, not measured) are: AHCI read 500 to 900 lines, NVMe read 600 to 1000, FAT32 write 800 to 1500, ext2 write 1500 to 2500, xHCI keyboard 2000 to 3000 and virtio-net plus smoltcp 600 to 900. Use them only for ordering. Against a 512-byte headroom every one of them is blocked until the size question is settled.

The keyboard is the highest-stakes driver. UEFI `ConIn` works only before ExitBootServices, so the Dawn menu can accept keys on a USB-only laptop but the shell cannot (inference from the supplied facts and the notes' reading of `src/uefi.rs`). "PS/2 emulation" on USB-only PCs is firmware behaviour (legacy USB support and port 60/64 emulation), not something the OS can rely on (motherboard manuals and a Linux mailing-list opinion, snippets). The OS-side work is: find the xHCI controller, perform the BIOS-to-OS ownership handoff through the xHCI legacy-support capability, enumerate (Enable Slot, Address Device, descriptors, SET_CONFIGURATION), select the HID boot protocol and service the interrupt endpoint (inference; the register layouts were not read from the spec). Polling avoids needing MSI or IOAPIC for a first version (inference). The `xhci` crate (0.9.2, last released 2023-07-19, `no_std`) covers registers and contexts only, not enumeration or HID ([docs.rs xhci](https://docs.rs/crate/xhci/latest)), and whether it builds on Rust 1.85 was not tested.

AHCI is the simpler storage target. The OSDev steps are: map ABAR (BAR5) uncacheable, set GHC.AE, find ports with `PxSSTS.det = 3` and signature `0x00000101`, stop the port, program `PxCLB`/`PxFB`, build a command table, restart the port and issue READ DMA EXT ([osdev.wiki AHCI](https://osdev.wiki/wiki/AHCI)). That page admits bugs in its own example (no timeout, 64-bit pointers cast to 32-bit). NVMe needs admin and I/O queues first: reset and configure CC, set AQA/ASQ/ACQ, Identify, Create I/O CQ and SQ, then Read (0x02) and Write (0x01) with PRPs; the wiki's PRP2 = 0 example only covers up to two pages ([osdev.wiki NVMe](https://osdev.wiki/wiki/NVMe)). PCI class codes are 01:06:01 for AHCI and 01:08:02 for NVMe ([osdev.wiki PCI](https://osdev.wiki/wiki/PCI)). The owner's real-PC test found no disk because only virtio-blk exists (`G:\Aeon\OS\docs\HANDOFF.md`, project file).

For writes, FAT32 is the cheapest step from the current read-only FAT code, and the `fatfs` crate supports read/write on FAT12/16/32 with `no_std` ([rust-fatfs](https://github.com/rafalh/rust-fatfs), snippet). Every FAT write touches the FAT and a directory entry, so a power cut can leave a lost chain; writing data before the FAT update and checking on boot is the proposed mitigation (inference, no source). `ext4-view` is read-only by design, so it does not help for writes ([ext4-view](https://docs.rs/crate/ext4-view/latest)). Journalling is a separate large project with no sourced size. For networking, `smoltcp` 0.13.1 is `no_std` and heap-free, and leaves the device layer to the driver ([smoltcp 0.13.1 source](https://docs.rs/crate/smoltcp/0.13.1/source/src/lib.rs)). Its MSRV for that version was not found. All of these crates depend on the open crate-policy decision.

## 3. Framebuffer console: Aeon's mode choice matches Linux, the gaps are robustness and speed

Aeon picks the largest GOP mode. That is what Linux's `auto` mode does: `match_auto()` keeps the mode with the largest width times height, ties broken by bits per pixel, with no cap ([Linux gop.c](https://github.com/torvalds/linux/blob/master/drivers/firmware/efi/libstub/gop.c)). Linux also skips `PIXEL_BLT_ONLY` modes, prefers the GOP that carries the ConOut GUID, reads EDID from the active protocol and then the discovered one, and computes pitch from `PixelsPerScanLine`, not `HorizontalResolution`. The rust-osdev bootloader writer handles only RGB, BGR and U8 and panics on bitmask formats ([bootloader framebuffer.rs](https://github.com/rust-osdev/bootloader/blob/main/common/src/framebuffer.rs)). So the checklist items are: reject BltOnly, handle bitmask formats, use the scan-line pixel count for pitch, and log the chosen mode. Whether Aeon does these is not in the supplied facts; verify. Largest area is not guaranteed native: a panel may scale or pillar-box it, and confirming native timing needs EDID preferred timing, which was not researched (inference). Limine allows an explicit per-entry `resolution:` that calls `SetMode` ([Limine commit mirror](https://code.ornl.gov/nix/nixpkgs/-/commit/ffffc8aaa1191c2a910b60c459c16ac9e053d283), snippet), and the notes recommend the same model: enumerate, prefer EDID-native, fall back by aspect ratio, allow an override (inference). One firmware-guidance claim (EDID native, then same aspect ratio, never below 1024x768) comes from an unverified search summary of an MSDN page.

Resolution changes are boot-time only. Linux's efifb takes the firmware mode and a different mode means a different option "for the next boot" ([Linux efifb docs](https://docs.kernel.org/fb/efifb.html)). Runtime modesetting needs a real GPU driver, and GOP is a boot-services protocol that cannot be relied on after ExitBootServices; both statements are from memory, not fetched (inference). Build the console so the grid and buffers are a function of the mode info, so a later driver can call the same code.

Speed matters at 4K, where one frame is 3840 x 2160 x 4 = 33,177,600 bytes, about 31.6 MiB (arithmetic). Linux's efifb offers `nowc` because write-combined mapping can slow other cores under heavy console output ([Linux efifb docs](https://docs.kernel.org/fb/efifb.html)); PAT/MTRR and `EFI_MEMORY_WC` were not researched. The standard design is a RAM shadow buffer with one bulk copy per frame, scrolling by memmove inside the shadow and never reading VRAM (inference, no fetched source). The shadow buffer must be allocated before ExitBootServices or from the kernel's own pool (inference). The bootloader crate writes pixels one at a time with volatile reads and clears the screen at the bottom; blog_os scrolls VGA text by copying rows up. Both are examples of the simple path and lose history ([bootloader framebuffer.rs](https://github.com/rust-osdev/bootloader/blob/main/common/src/framebuffer.rs); [blog_os VGA text mode](https://os.phil-opp.com/vga-text-mode/)). Aeon already has wrapped line editing, which most references lack.

Remaining terminal work is scrollback and an escape parser. Scrollback needs a text-cell ring buffer separate from pixels (inference). For escape sequences, the `vte` crate (0.15.0) implements Paul Williams' ANSI parser state machine ([docs.rs vte](https://docs.rs/vte/latest/vte/); [vt100.net parser](https://vt100.net/emu/dec_ansi_parser)), but whether it is `no_std` was not shown and the crate-policy decision applies. DEC mode 7 (auto-wrap) and mode 45 (reverse wraparound) exist in xterm ([xterm ctlseqs](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)), but their exact behaviour, including the usual deferred "pending wrap" in the last column, was not confirmed because the page was truncated; treat that behaviour as from memory. For fonts, `noto-sans-mono-bitmap` is `no_std`, allocation-free and offers 16, 20, 24 and 32 px rasters ([docs.rs](https://docs.rs/noto-sans-mono-bitmap/latest/noto_sans_mono_bitmap/)). Linux picks a default console font by a score that prefers bigger fonts at high resolution ([Linux fonts.c](https://github.com/torvalds/linux/blob/master/lib/fonts/fonts.c)). No source gives HiDPI thresholds, so any threshold, such as 16 px under 1080 lines and 32 px at 2160, is a starting guess (inference). A bitmap font set also costs image bytes, so it competes with the 512-byte headroom.

## 4. Boot splash: draw it, do not embed it

Apple's own support page describes the pattern to imitate: the logo appears when the Mac finds its startup disk, then "a progress bar, with or without the Apple logo", which may alternate with blank screens ([Apple Support](https://support.apple.com/en-us/102535)). Plymouth's `spinner` and `bgrt` themes are the Linux analogues, with `bgrt` keeping the vendor logo ([Arch Wiki, Plymouth](https://wiki.archlinux.org/title/Plymouth), snippet), and Android boot animations are frame sequences in a zip ([AOSP FORMAT.md](https://android.googlesource.com/platform/frameworks/base/+/master/cmds/bootanimation/FORMAT.md), snippet). The common thread is a dark field, one small mark and nothing else (inference); no source gives sizes, fade durations or contrast ratios, so every numeric choice below is a design choice, not a sourced rule.

The sourced technical hook is ACPI BGRT. The table has version at 0x24 (must be 1), status at 0x26, image type at 0x27 (0 = BMP), a physical image address at 0x28 and X and Y offsets at 0x30 and 0x34; status bit 0 says the firmware displayed the image and bits 1 to 2 give a clockwise rotation ([osdev.wiki BGRT](https://osdev.wiki/wiki/BGRT)). Linux exposes the same fields under `/sys/firmware/acpi/bgrt/` and describes the purpose as letting splash software avoid jarring screen changes ([Linux sysfs ABI](https://grok.openbmc.org/xref/openbmc/linux/Documentation/ABI/testing/sysfs-firmware-acpi?r=d1ff4b1c), snippet). A reader is small: find "BGRT", require version 1, status bit 0 and type 0, reject a zero address, parse the BMP header and draw at (X, Y), rotating per the status bits (inference). Copying the image early, before firmware memory is reclaimed, is safer (inference). Whether Windows uses BGRT was not searched.

For Aeon, the size limit decides the design. A 256 x 256 8-bit alpha mask is 64 KiB raw, a quarter of the whole image budget (arithmetic from the notes). BGRT costs zero embedded bytes and gives continuity with the firmware logo. Where there is no BGRT image, draw a simple logo procedurally (rings or arcs) at a size scaled by screen height over a 1080 reference, preferring integer multiples (inference). The progress element is cheap: a thin bar is one rectangle redrawn per tick, a spinner is a few precomputed masks cycled per frame (inference). Plain sRGB blending on a dark background is cheaper than linear-light blending and usually acceptable (inference). BMP is the simplest decoder path (`tinybmp` 0.7.0, `no_std` ([docs.rs tinybmp](https://docs.rs/tinybmp/latest/tinybmp/index.html), snippet)), and `minipng` decodes PNG with no dependencies ([lib.rs minipng](https://lib.rs/crates/minipng), snippet); either is a crate-policy question and a size cost.

Timing and safety rules rest on inference alone. Keep one GOP mode from Dawn through the kernel, since a mode switch after handoff is a documented flicker source in one Limine case ([bkhome.org](https://bkhome.org/news/202209/limine-resolution-fix-in-initrd.html), blog). Show the splash only as long as early init takes, with no artificial wait unless a fade needs it. Keep an Esc or F2 key to skip to verbose text, make the splash non-blocking and bounded by a timeout, and never let it own the only copy of an error. No accessibility guidance (motion, contrast) was found.

## 5. Testing and security: run what exists, then fuzz the parsers

Aeon's 247 host tests and 364 QEMU checks are strong for a hobby kernel, but a CI file that has never run proves nothing about them. Run it first; the OVMF and QEMU install steps for GitHub Actions are not sourced in the notes. Next, cargo-fuzz drives libFuzzer on x86-64 Linux or macOS hosts only ([Rust Fuzz Book](https://rust-fuzz.github.io/book/print.html)), so the FAT, ELF and event-log parsers must build for the host. That the tool needs nightly comes from a secondary page ([cargo-fuzz skill page](https://www.claudepluginhub.com/skills/commit-ai-testing-handbook-skills-plugins-testing-handbook-skills/cargo-fuzz), secondary). Miri catches out-of-bounds access, use-after-free, uninitialized reads and misaligned references, but it "tests one of many possible executions" and cannot run MMIO, page tables or inline assembly, so it covers only the host-testable slice ([rust-lang/miri](https://github.com/rust-lang/miri)). `clippy::undocumented_unsafe_blocks` has existed since 1.58.0 and enforces `// SAFETY:` comments, with known false positives ([Clippy lint source](https://rust.googlesource.com/rust-clippy/+/refs/heads/beta/clippy_lints/src/undocumented_unsafe_blocks.rs); [clippy #15915](https://github.com/rust-lang/rust-clippy/issues/15915)). proptest gives round-trip tests in ordinary `cargo test` ([proptest](https://docs.rs/crate/proptest/latest/source)). Loom is conditional on multi-CPU lock-free code and has false alarms and incomplete exploration ([loom README](https://docs.rs/crate/loom/0.7.1/source/README.md)), so it only matters once SMP exists. The ranking is the researchers' judgment: CI, Miri, fuzzing, the Clippy lint, proptest, then supply-chain checks, which were not researched.

Hardening has the thinnest evidence. SMEP stops supervisor-mode fetches from user-accessible addresses and SMAP stops accidental kernel access to user memory ([Linux self-protection doc](https://gitweb.dragonflybsd.org/linux.git/blob/f4a8871f9f347b185c44525c9bb1755951f94841:/Documentation/security/self-protection.rst)). Linux pins the SMAP, SMEP and UMIP bits in `native_write_cr4` so exploits cannot clear them ([Phoronix](https://www.phoronix.com/news/Linux-Protect-Special-CR4-Bits)). Applying the same pinning, and a QEMU check that fails when a bit is clear, follows from Linux's stated design goal that protections have tests (inference). The notes record Aeon as already enabling SMEP, SMAP and UMIP, but the supplied owner facts mention only W^X, so verify. Sources disagree on UMIP's Linux default (enabled by default in the 2017 patch series, disabled by default in a later commit), so do not copy either default blindly ([LKML v10](https://lkml.iu.edu/hypermail/linux/kernel/1710.3/03405.html); [LKML runtime-enable](https://lkml.iu.edu/hypermail/linux/kernel/1711.1/00325.html)). **KASLR, stack canaries, CET and shadow stacks, retpolines, IBRS, KPTI and reproducible builds were not researched at all**, so this report gives no claim about their value or cost for Aeon.

## What is not verified

Sources and access. Several primary pages could not be read: the GRUB timeout-style page (HTTP 429 twice), uefi.org (HTTP 403, so the UEFI GOP, memory-map and boot-manager sections and the ACPI spec were not read directly), wiki.osdev.org (403, so the osdev.wiki mirror was used, and the ext2 and virtio-net pages were not read), and the Plymouth, Microsoft BCDEdit and systemd sd-boot pages (blocked or partial). The Intel xHCI and AHCI specs, the NVMe base spec, the Microsoft FAT spec, the TCG PC Client profile and the Intel SDM and AMD APM were never fetched, so register details come from OSDev wiki pages and snippets only. The fetch tool summarised pages, so quoted wording should be checked against the source before it goes into code or docs.

Missing numbers. No source gives firmware, loader or kernel boot times, a recommended splash duration, HiDPI scaling thresholds, LOC counts or days of work for any component. Default timeouts for GRUB, rEFInd and Windows, and systemd-boot's default of 0, were not read from primary pages. Driver size estimates and the S/M/L labels in section 6 are unsourced.

Conflicts and stale data. The blog_os status page runs through September 2026 on one fetch, while another note found the newest "This Month in Rust OSDev" is July 2026; unresolved. Theseus's README says "under active development" but its last push is 2024-09-22. Limine's protocol revision count differs between the v7.x and current repos (version drift), and the `limine` crate README says base revision 6. UMIP's Linux default differs between two LKML sources. Redox, Theseus, SerenityOS, Hermit and MikanOS feature claims are mostly directory names, not code, and Theseus internals were not read. Not researched: KASLR, stack canaries, CET, retpolines, IBRS, KPTI, cargo-llvm-cov and cargo-mutants, cargo-deny and cargo-vet, Windows BGRT use, and ChromeOS splash. SYSRET with a non-canonical RCX as a privilege-escalation class (CVE-2012-0217) came from memory in the notes and is not sourced. Whether `xhci` 0.9.2 builds on Rust 1.85, and whether `vte` is `no_std`, are untested.

## Conclusion

The checklist exercise shows that Aeon's weakness is not a missing textbook feature but a coupling: the one-image design, the 256 KiB limit and the no-crates question all feed into whether the real-hardware drivers can exist at all. That makes the size and crate decision the true first item of any plan, ahead of the first line of driver code, and it means an ELF loader is as much a space-recovery step as a feature (inference).

The evidence is also lopsided. Boot menu, GOP mode choice, BGRT and storage drivers have good primary or wiki sourcing, while hardening, SMP internals and effort estimates have almost none. A developer turning the gap table into a plan should treat items 1 to 7 as ready to schedule, items 8 to 11 as ready with minor reading, and items 12 to 16 as needing their own research pass before any commitment.
