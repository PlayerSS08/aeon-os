# Building a Calm Apple-Style Boot Picker

Aeon's planned picker is safe to build, but it departs from every mainstream boot manager the research could document. **GRUB, systemd-boot, rEFInd and Windows all boot a configured default when the timer ends, not the highlighted entry. None of them restarts the timer on navigation.** GRUB documents that a key press stops the timer ([GNU GRUB manual](https://www.gnu.org/software/grub/manual/grub/grub.html)). None documents any guard against a disruptive default, and Apple documents no countdown at all. So "15 seconds, highlight runs on timeout, restart on each arrow key" is a new design, not a convention. It is defensible if two rules hold. Only Boot and Recovery may ever start from the countdown. The screen must always say, in words, what will start. For the rest of the picker, Apple's guidance supports short plain wording, dim neutral greys, 4.5:1 minimum contrast and no technical data on failure screens. Apple's actual picker layout, keyboard model and panic-screen colours are not documented in any source found, so the Apple look has to be reconstructed. Facts below come from fetched sources. Items marked "Inference" are design judgement.

## The countdown is a new design, so make it safe

**Source-backed.** GRUB's default timeout is 5 seconds, and "Pressing a key interrupts the timeout" ([GNU GRUB manual](https://www.gnu.org/software/grub/manual/grub/grub.html)). systemd-boot shows no menu unless a timeout is set, and then boots "the default entry" ([loader.conf(5)](https://www.freedesktop.org/software/systemd/man/latest/loader.conf.html)). rEFInd boots its `default_selection`, or the previously booted entry if none is set ([rEFInd configuration reference](https://www.rodsbooks.com/refind/configfile.html)). Microsoft describes the timeout as the wait "before the boot manager selects a default entry" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/devtest/bcdedit--timeout)). The only disruptive timeout action found is rEFInd's opt-in `shutdown_after_timeout`. systemd-boot's `@saved` default silently re-selects whatever the user last chose, and the manual does not warn about that ([loader.conf(5)](https://www.freedesktop.org/software/systemd/man/latest/loader.conf.html)). A Libreboot U-Boot patch disables the timer once an arrow key is pressed ([patch 0004](https://browse.libreboot.org/lbmk.git/tree/config/u-boot/x86/patches/0004-Support-auto-boot-timeout-delay-bootflow-menu.patch)). Apple's support pages describe a held key (Option) or held power button and a click to confirm, with no timeout mentioned ([Apple Support HT201255](https://support.apple.com/en-us/HT201255)).

**Inference.** The honest summary for Aeon's documentation is: "Mainstream managers boot a stored default; Aeon boots whatever is highlighted, but only if it is Boot or Recovery." That gives the user one rule to learn. The 15-second length is longer than GRUB's 5 seconds, which suits slower reaction times, but no accessibility source was found to justify any particular value. Restarting the full 15 seconds on every arrow press is a way to let someone browse without losing the timer. It also means a stuck or bouncing key could hold the menu open indefinitely, which is a risk that is not covered by any source. Three safety rules follow. First, the auto-run set is a fixed whitelist of Boot and Recovery, checked in code at the moment the timer expires, not just at render time. Second, when the highlight sits on Restart, Power off or Firmware setup, the countdown line should be replaced by a "waiting for Enter" line, and the timer should stop rather than jump back to Boot. Third, the countdown text should name the entry and update with the highlight, for example "Aeon starts in 12 seconds." Naming the entry beats the Libreboot-style approach of silently disabling the timer, because the user can always see the current rule.

## Arrow keys and Enter only is the right model

**Source-backed.** Letter shortcuts exist as accelerators elsewhere, and they can start things instantly. In GRUB, "If a hotkey associated with a menu entry is pressed, it will boot the associated menu entry immediately" ([GNU GRUB manual](https://www.gnu.org/software/grub/manual/grub/grub.html)). rEFInd launches loaders on 1-9 and on letters, including any letter matching an OS name, and its Insert, F2, Tab and "+" keys open submenus ([rEFInd: Using rEFInd](https://rodsbooks.com/refind/using.html)). systemd-boot's search-snippet key list adds `e` for editing the command line and `t`/`T` for changing the timeout (not opened in full; [sd-boot(7)](https://manpages.ubuntu.com/manpages/kinetic/man7/sd-boot.7.html)), and its manual advises disabling the editor on machines others can reach ([loader.conf(5) via mankier](https://www.mankier.com/5/loader.conf)). Apple's HIG defines a shortcut as a primary key plus modifiers, allows single-key bindings only for games, and binds restart and shut down to three-key chords ([Apple HIG, Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards.md)). Apple's own picker is described as select-then-confirm ([Apple Support, mchlp1034](https://support.apple.com/guide/mac-help/start-up-your-mac-from-a-different-disk-mchlp1034/mac)). The uefi crate (0.41.0) lists Up as 0x01, Down as 0x02 and Escape as 0x17 ([uefi crate source](https://docs.rs/crate/uefi/latest/source/src/proto/console/text/input.rs)).

**Inference.** Combine that with an auto-run timer and a letter key becomes a one-keystroke launch with no chance to back out. Removing letters, digits, edit and timeout keys leaves a model with only three inputs (Up, Down, Enter), which is easy to test and to explain. Treat every other key, including Escape, as a no-op that does not even restart the countdown, so stray keys cannot extend the menu. Because the picker has no Escape-to-cancel, every non-launching entry should need an Enter. The Up and Down scan codes agree with the crate but are unconfirmed against UEFI 2.10 Appendix B, which returned HTTP 403. Wrapping behaviour at the list ends and the exact Enter encoding were not researched.

## Greys, sizes and one line of help

**Source-backed.** Apple's dark-mode guidance asks for a contrast ratio "no lower than 4.5:1" and 7:1 for small custom text, and says the dark palette uses "dimmer background colors and brighter foreground colors" ([Apple HIG, Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)). The published iOS dark greys are 1C1C1E, 2C2C2E, 3A3A3C, 48484A, 636366 and 8E8E93 (hex converted from Apple's RGB values), but Apple says not to hard-code colour values and notes they vary between releases, and these are not macOS values ([Apple HIG, Color](https://developer.apple.com/design/human-interface-guidelines/color)). Apple also warns against relying on colour alone ([same page](https://developer.apple.com/design/human-interface-guidelines/color)). WCAG 2.2 sets 4.5:1 for normal text, 3:1 for text of 18 pt or 14 pt bold, and says the ratio must not be rounded ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum)). Apple's macOS default text is 13 pt with a 10 pt minimum, and it advises avoiding light weights ([Apple HIG, Typography](https://developer.apple.com/design/human-interface-guidelines/typography)). No boot manager documents pixel sizes. Limine exposes font scale options ([Limine CONFIG.md](https://github.com/limine-bootloader/limine/blob/trunk/CONFIG.md)). No boot-menu source discusses a per-entry description line.

**Inference.** Use a near-black or 1C1C1E background, 2C2C2E or 3A3A3C for the highlight, near-white for the entry name and 8E8E93 for the description. My hand calculation (to be asserted in unit tests) puts 8E8E93 on 1C1C1E at about 5.2:1, which passes, but on a 3A3A3C highlight at about 3.5:1, which fails. So the description line should sit outside the highlight bar, and the highlighted name should stay near-white (about 11:1). Add a non-colour cue such as a leading marker or a shape so selection survives colour loss. For sizes, scale from the vertical resolution with an unsourced rule of item height = max(16 px, height/45). That gives roughly 24 px at 1080p and 48 px at 2160p, with titles near 1.5x and the description near 0.8x, so about 19 px and 38 px for the description. Check these on real panels, since the rule is untested. Use a regular or medium weight font, and rasterise an open font such as Inter rather than Apple's SF, whose licence forbids embedding ([Apple Developer, Fonts](https://developer.apple.com/fonts/)). Inter's README and the standard OFL wording differ on selling derivatives ([Inter on GitHub](https://github.com/rsms/inter)), so read its LICENSE file first. Keep one description line directly under the list and limit list width so long names do not stretch across a 4K screen.

## A panic screen that says little

**Source-backed.** Apple moved away from on-screen panic detail. Mac OS X 10.2 to 10.7 dropped a grey curtain over the display with a multilingual restart message, and from 10.8 the user learned of a panic only after an automatic restart, with the log offered later ([Eclectic Light](https://eclecticlight.co/2024/07/27/a-brief-history-of-kernel-panics/)). Wikipedia differs on the 10.2 colours and on what 10.8 and later show after restart ([Wikipedia](https://en.wikipedia.org/wiki/Kernel_panic)). The current alert reads "Your computer was restarted because of a problem", and the advice lives in a support article ([Apple Support 102382](https://support.apple.com/en-us/102382)). Apple's writing guidance says to avoid blame, say what someone can do, skip "oops", avoid "we" and use fewer words ([Apple HIG, Writing](https://developer.apple.com/design/human-interface-guidelines/writing)). Windows shows a stop code and module name ([Microsoft Learn](https://learn.microsoft.com/windows-hardware/drivers/debugger/bug-checks--blue-screens-)). Linux's drm_panic moves detail into a QR code (Kconfig and patch snippets only).

**Inference.** For Aeon, show a muted grey screen with a short title such as "Aeon stopped unexpectedly", one sentence on what to do ("Restart your computer. Choose Recovery if it happens again."), and nothing else on screen: no addresses, register dumps or hex. Save the detail to a log or serial output. A short reason word is optional, but a QR code is not needed, and no source supports adding one. Do not use saturated red. Apple's red is a system accent, not a documented panic colour.

## Open gaps

The notes could not confirm any of the following. Apple's Startup Manager layout, whether arrow keys and Return work on Apple silicon, and any Escape behaviour. Any Apple boot-screen timing or exact black value. Current Windows 10/11 arrow-key behaviour, since the Windows 30-second default and arrow-key stop rest on forum snippets and a Windows 2000 book. systemd-boot's behaviour for key presses during a countdown. Any accessibility source for timeout length, including WCAG's timing guidance, which was not searched. Pixel sizes and layout ratios, which are inference only. Firmware setup keys and list position across vendors. The primary UEFI spec text for scan codes. The kernel.org drm_panic documentation, which returned 404.

## Conclusion

Aeon's design gets its safety from structure, not from convention. A fixed two-entry auto-run whitelist, a countdown line that names the live highlight and a three-key input model together replace the "stored default" that mainstream managers rely on. These are Aeon's own rules, and the documentation should say so rather than claim Apple or GRUB precedent. Contrast is where a small test pays off. The grey text that passes on the base panel fails on the highlight, so automated contrast checks on every colour pair are worth adding before any visual polish.
